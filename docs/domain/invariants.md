# 도메인 규칙

이 문서는 구현 중 유지해야 하는 핵심 도메인 규칙을 정리합니다. 기능 구현이나 리팩터링 중 아래 규칙이 깨지면 데이터 의미가 달라지므로 PR에서 반드시 확인합니다.

## 사용자와 기본 리소스

- 사용자는 1개의 옷장을 가집니다.
- 사용자는 1개의 코디북을 가집니다.
- 사용자 생성 또는 온보딩 완료 시 옷장과 코디북 생성 기준이 함께 맞아야 합니다.
- 사용자별 데이터 조회/수정은 인증 사용자와 요청 대상 사용자가 일치해야 합니다.

## 공통 옷 정보와 사용자 옷장 정보

- `CLOTHES`는 옷 자체의 공통 정보입니다.
- `WARDROBE_CLOTHES`는 사용자 옷장과 공통 옷 정보를 연결하는 사용자별 정보입니다.
- `USERS.gender`는 사용자 프로필 성별이고, `CLOTHES.gender`는 옷 대상 성별입니다. 두 값은 서로 다른 도메인 의미를 가지며 같은 필드처럼 취급하지 않습니다.
- `CLOTHES.gender`는 사용자 화면 표시나 사용자가 직접 수정하는 값이 아니라, 옷 분류/추천과 저장 요청에 사용하는 내부 code입니다.
- 보유/미보유 상태는 `WARDROBE_CLOTHES.ownership_status`로 관리합니다.
- 옷장에서 옷을 삭제해도 `CLOTHES` 공통 정보는 삭제하지 않습니다.
- 옷장 삭제는 사용자와 옷의 연결을 제거하거나 비활성화하는 동작으로 봅니다.
- 공통 옷 정보가 정교하게 누적될수록 추천 품질이 높아지므로, 검증된 옷 정보는 서비스 데이터로 유지합니다.

## 옷 정보 출처

- 공통 옷 정보의 출처는 `CLOTHES.clothes_info_source`로 관리합니다.
- 옷 정보 출처 값은 `PHOTO`, `PURCHASE_HISTORY`, `EXTERNAL_SHOPPING`입니다.
- `PHOTO`는 사용자가 직접 촬영하거나 업로드한 옷 사진 기반 등록입니다.
- `PURCHASE_HISTORY`는 사용자가 구매내역 캡처 이미지를 업로드한 등록입니다.
- `EXTERNAL_SHOPPING`은 네이버쇼핑 등 외부 쇼핑몰 상품 정보 기반 등록입니다.
- 외부 쇼핑몰 상품인 경우 `external_source`, `external_product_id`, `external_product_url`을 가능한 범위에서 함께 저장합니다.

## 이미지 저장

- 옷 이미지, 사용자 업로드 이미지, 구매내역 캡처, 피드 이미지는 AWS S3 저장 기준으로 관리합니다.
- 사용자 옷장에서 옷을 삭제해도 공통 옷 이미지와 공통 옷 정보는 삭제하지 않습니다.
- 이미지 URL은 API 응답에서 클라이언트가 표시할 수 있는 문자열로 내려갑니다.

## 스타일과 색상

- 옷 하나는 대표 스타일 1개와 보조 스타일 여러 개를 가질 수 있습니다.
- 옷 하나는 대표 색상 1개와 보조 색상 여러 개를 가질 수 있습니다.
- 스타일과 색상은 서비스에서 지정한 카탈로그 값 안에서 선택합니다.
- 별도의 임의 개수 제한은 두지 않고, 중복 없이 카탈로그 전체 범위까지 선택할 수 있습니다.
- 현재 API validation 기준은 보조 색상 최대 12개, 스타일 최대 10개입니다.
- 같은 옷에 같은 스타일 또는 같은 색상을 중복 연결하지 않습니다.
- 대표 스타일/색상은 `PRIMARY`, 보조 스타일/색상은 `SECONDARY`로 구분합니다.
- `sort_order`는 표시 순서와 입력 순서를 안정적으로 재현하기 위해 사용합니다.

## 카탈로그 저장과 표시

- 카테고리, 아이템 타입, 색상, 스타일은 API와 DB에서 영문 `code` 값을 사용합니다.
- 화면 표시명은 한글 label을 사용하며, DB 저장값으로 사용하지 않습니다.
- 색상 HEX 값은 UI 표시용 값이며, DB 저장 기준값은 색상 code입니다.
- `item_type`은 선택한 `category`에 속한 코드만 사용할 수 있습니다.
- 밝은 색상 표시처럼 UI 보정이 필요한 규칙은 FE에서 처리하되, 색상 code와 HEX 값은 BE 카탈로그 기준을 따릅니다.
- 카탈로그 값이 변경되면 enum, API 응답, [카탈로그 사용 가이드](./catalog.md), 도메인 용어집을 함께 갱신합니다.

## 스타일 점수

- 대표 스타일은 7점, 보조 스타일은 각각 3점으로 계산합니다.
- 대표 색상은 7점, 보조 색상은 각각 3점으로 계산합니다.
- 온보딩 또는 마이페이지에서 사용자가 여러 스타일을 선택하면 첫 번째 선택은 대표 스타일, 나머지는 보조 스타일로 봅니다.
- 사용자가 선택한 선호 스타일 점수는 `USER_STYLES.preference_weight`에 반영합니다.
- 사용자의 옷장에 등록된 옷 스타일 점수는 `USER_STYLES.wardrobe_weight`에 반영합니다.
- 추천 싫어요 또는 추천 제외 피드백은 대표 스타일 -7점, 보조 스타일 각각 -3점으로 `USER_STYLES.feedback_weight`에 반영합니다.
- 최종 스타일 점수는 `combined_weight = preference_weight + wardrobe_weight + feedback_weight` 기준으로 계산합니다.
- 점수가 같은 추천 후보는 같은 점수 그룹 안에서 랜덤 노출합니다.

## 추천 피드백과 제외

- 추천 싫어요는 사용자가 해당 옷 또는 상품에 비선호를 표시한 기록입니다.
- 추천 제외는 사용자가 해당 옷 또는 상품을 이후 추천에서 제외하겠다는 강한 비선호 기록입니다.
- 추천 제외된 옷은 사용자 추천 후보에서 영구 제외합니다.
- 추천 제외도 추천 싫어요와 동일하게 스타일 점수에 마이너스 피드백을 반영합니다.
- 추천 피드백은 사용자별로 관리하며 다른 사용자 추천에는 영향을 주지 않습니다.

## 코디와 코디북

- 코디는 코디북에 저장됩니다.
- 코디는 여러 옷을 `OUTFIT_ITEMS`로 연결합니다.
- 코디 구성에는 사용자가 보유한 옷과 미보유 옷이 모두 포함될 수 있습니다.
- 코디 수정은 기존 코디의 정보와 구성 아이템을 직접 수정하는 방식을 기본으로 합니다.
- 코디 스타일은 구성 옷의 스타일 정보를 바탕으로 대표/보조 스타일을 관리합니다.

## 룩피드

- 룩피드 게시글은 코디와 연결될 수 있습니다.
- 피드 이미지는 최소 1장 이상을 기준으로 합니다.
- 좋아요, 댓글/대댓글, 저장, 팔로우는 사용자별 상호작용으로 관리합니다.
- 피드 게시글은 숨김 상태와 삭제 시점을 관리할 수 있습니다.

## API 경로

- `/api/v1` 경로가 존재하는 API는 `/api/v1`을 우선 사용합니다.
- `/api/v1` 경로가 없는 API는 현재 구현된 `/api` 경로를 사용합니다.
- 경로 통일이 필요한 API는 별도 PR에서 기존 경로와 FE 사용처를 함께 확인합니다.
